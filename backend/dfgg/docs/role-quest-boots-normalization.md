# 역할 퀘스트 신발 정규화 결정 기록

## 1. 배경

ChampionBuildStats는 두 Riot API 응답을 결합해 코어 아이템 빌드 순서를 만든다.

- Match-v5 상세의 `item0`부터 `item5`까지를 최종 보유 아이템으로 사용한다.
- BOTTOM은 퀘스트 완료 후 신발이 일반 인벤토리에서 빠지므로 Match의 `roleBoundItem`도 최종 보유 아이템에 포함한다.
- Timeline의 `ITEM_PURCHASED`, `ITEM_SOLD`, `ITEM_UNDO` 이벤트로 실제 구매 순서를 복원한다.
- Match의 최종 아이템을 Timeline에서 모두 확인할 수 있을 때만 완전한 구매 순서로 저장한다.

일반 아이템은 이 방식으로 최종 상태와 구매 이력을 연결할 수 있지만, 2026 역할 퀘스트의 신발 처리에는 예외가 있다.

### MID

MID 퀘스트가 완료되면 2티어 신발이 3티어 신발로 자동 업그레이드된다. Match에는 최종 3티어 신발 ID가 저장되지만, Timeline에는 해당 3티어 신발의 `ITEM_PURCHASED` 이벤트가 없을 수 있다.

확인한 `KR_8337955228`의 참가자 3 사례는 다음과 같다.

```text
485453  ITEM_PURCHASED  1001  // 장화
691475  ITEM_DESTROYED  1201  // MID 퀘스트 완료
779522  ITEM_DESTROYED  1001
779522  ITEM_DESTROYED  3020
779522  ITEM_PURCHASED  3020  // 마법사의 신발
```

최종 Match에 3티어 신발 `3175`가 있더라도 Timeline에는 `3175`를 획득한 이벤트가 없다. 따라서 Match의 최종 ID와 Timeline의 구매 ID를 그대로 비교하면 구매 순서 계산이 실패한다.

### BOTTOM

BOTTOM 퀘스트는 신발을 업그레이드하지 않고 Role Quest 전용 슬롯으로 이동시킨다. Timeline에는 별도의 슬롯 이동 이벤트가 없으며, 퀘스트 아이템과 기존 신발의 `ITEM_DESTROYED` 이벤트만 나타난다.

```text
413211  ITEM_PURCHASED  1001
563921  ITEM_PURCHASED  3020
727136  ITEM_DESTROYED  1202  // BOTTOM 퀘스트 완료
727136  ITEM_DESTROYED  3020  // Role Quest 슬롯으로 이동
```

Match의 `roleBoundItem`에는 기존 신발 ID인 `3020`이 유지되므로 Timeline의 이전 `ITEM_PURCHASED 3020`과 직접 연결할 수 있다.

## 2. 검토한 대안

### 대안 A: Timeline에 가상 3티어 신발 이벤트 추가

MID 퀘스트 완료와 신발 이벤트를 조합해 실제 API에는 없는 3티어 신발 획득 이벤트를 생성한다.

```text
실제 Timeline:  ITEM_PURCHASED 3020
추론 이벤트:   ITEM_PURCHASED 3175
```

3티어 신발의 추론 획득 시점은 다음과 같이 계산할 수 있다.

```text
3티어 신발 획득 시점 = max(2티어 신발 획득 시점, MID 퀘스트 완료 시점)
```

| 장점 | 단점 |
| --- | --- |
| Match의 실제 최종 3티어 신발 ID와 Timeline 목록을 그대로 비교할 수 있다. | Riot API에 존재하지 않는 이벤트를 데이터에 추가한다. |
| 실제 최종 인벤토리와 구매 순서 양쪽에서 3티어 ID를 유지할 수 있다. | 실제 이벤트와 추론 이벤트를 구분하는 출처 정보가 필요하다. |
| 향후 3티어 신발 획득 시점이 필요한 분석에 사용할 수 있다. | 퀘스트 완료 전후의 신발 구매, 판매, 되돌리기, 재구매를 모두 고려해야 한다. |
| | Riot의 이벤트 표현이 변경되면 추론 규칙이 잘못된 이벤트를 만들 수 있다. |
| | 현재 요구사항에는 3티어 업그레이드 시점이 필요하지 않아 복잡도 대비 효용이 작다. |

### 대안 B: Match의 3티어 신발을 2티어 신발로 정규화

Match의 최종 아이템에서 지원하는 3티어 신발을 발견하면, 구매 순서 비교에 사용하는 정규화 목록에서는 플레이어가 구매한 신발 ID로 치환한다.

```text
Match 실제 최종 아이템: 3175
비교용 정규화 아이템:   3020
Timeline 구매 이벤트:   3020
```

| 장점 | 단점 |
| --- | --- |
| Timeline에 없는 이벤트를 만들지 않는다. | 정규화된 최종 아이템 목록만 보면 실제 3티어 상태를 알 수 없다. |
| 기존 구매 순서 계산기를 작은 변경으로 유지할 수 있다. | 3티어 신발의 효과나 업그레이드 시점을 분석하려면 원본 Match를 다시 사용해야 한다. |
| 구매 선택이 발생한 2티어 신발을 기준으로 통계를 일관되게 집계한다. | 패치에 따라 달라질 수 있는 2티어와 3티어의 대응 관계를 관리해야 한다. |
| 같은 신발 선택이 2티어와 3티어로 나뉘어 별도 빌드로 집계되는 것을 막는다. | 필드명이 `finalCoreItemIds`라면 실제 최종 상태가 아니라 비교용 상태라는 의미 차이가 생길 수 있다. |
| 모든 포지션의 신발 구매 통계를 동일한 구매 ID 기준으로 조회할 수 있다. | |

## 3. 결정

대안 B를 선택한다. 현재 통계에서 필요한 정보는 플레이어가 어떤 신발을 선택했고 전체 빌드에서 언제 구매했는지이며, 퀘스트로 자동 적용된 3티어 업그레이드 시점은 필요하지 않다.

다음 원칙을 적용한다.

1. `raw_matches`와 `raw_match_timelines`의 Riot 원본 JSON은 변경하지 않는다.
2. Match를 `NormalizedMatch`로 변환할 때 비교용 최종 코어 아이템 목록만 정규화한다.
3. 포지션과 관계없이 최종 아이템이 지원하는 3티어 신발이면 대응하는 구매 신발 ID로 치환한다.
4. Timeline에는 실제로 존재하는 2티어 신발 구매 이벤트만 사용한다.
5. `ITEM_DESTROYED`를 일반적인 보유 아이템 제거로 해석하지 않는다. 조합 재료 소모, 역할 퀘스트 완료, BOTTOM 전용 슬롯 이동에도 같은 이벤트가 사용되기 때문이다.
6. 실제 최종 3티어 신발이 필요하면 보존된 `raw_matches`에서 확인한다.

이 결정으로 구매 순서와 `buildKey`에는 플레이어가 구매한 신발 ID가 저장된다. 3티어 신발은 자동 업그레이드 상태이므로 별도의 플레이어 빌드 선택으로 집계하지 않는다.

## 4. 정규화 규칙

### 3티어 신발

현재 아이템 메타데이터 기준 대응 관계는 다음과 같다.

| 3티어 신발 | 비교용 2티어 신발 |
| --- | --- |
| `3168` Immortal Path | `3008` Gluttonous Greaves |
| `3170` Swiftmarch | `3009` Boots of Swiftness |
| `3171` Crimson Lucidity | `3158` Ionian Boots of Lucidity |
| `3172` Gunmetal Greaves | `3006` Berserker's Greaves |
| `3173` Chainlaced Crushers | `3111` Mercury's Treads |
| `3174` Armored Advance | `3047` Plated Steelcaps |
| `3175` Spellslinger's Shoes | `3020` Sorcerer's Shoes |
| `3176` Forever Forward | `3010` Symbiotic Soles |

`3176`은 `3010 → 3013 → 3176`으로 자동 변환되므로 바로 이전 단계인 `3013`이 아니라 플레이어가 구매한 `3010`을 비교 ID로 사용한다.

가능하면 고정된 숫자 목록보다 아이템 메타데이터의 업그레이드 관계(`from`/`into`)를 사용한다. 현재 `items` 테이블이 관계를 보존하지 않는다면 명시적인 불변 매핑을 두고 각 대응 관계를 테스트한다. 자동 변환 단계가 둘 이상인 신발은 Timeline에 나타나는 구매 ID까지 관계를 따라가야 한다.

정규화는 포지션과 관계없이 적용한다. 이 규칙의 목적은 MID 퀘스트 완료 여부를 판별하는 것이 아니라, 최종 3티어 신발을 플레이어가 실제로 선택하고 구매한 신발 ID로 통일하는 것이다. 따라서 `teamPosition`을 확인하거나 `ITEM_DESTROYED 1201` 이벤트로 퀘스트 완료를 검증하지 않는다.

이 방식은 포지션 값 누락이나 역할 교환의 영향을 받지 않고, 다른 시스템을 통해 3티어 신발을 얻은 과거 데이터도 같은 구매 기준으로 집계한다. 실제 3티어 상태는 Raw Match에 남아 있으므로 정규화 통계에서만 정보가 축약된다.

### BOTTOM

BOTTOM은 3티어 정규화를 적용하지 않는다.

```text
비교용 최종 아이템 = item0 ~ item5 + roleBoundItem
구매 시점 = Timeline에서 같은 신발 ID의 기존 ITEM_PURCHASED 시점
```

퀘스트 완료와 같은 시각에 나타나는 신발의 `ITEM_DESTROYED`는 Role Quest 슬롯 이동으로 발생할 수 있으므로 구매 순서에서 제거하지 않는다.

### 그 외 포지션

기존과 동일하게 Match의 `item0`부터 `item5`까지만 최종 코어 아이템 후보로 사용한다. `roleBoundItem`은 각 역할의 퀘스트 상태를 나타낼 수 있지만, 현재 요구사항에서는 BOTTOM 신발만 최종 빌드에 추가한다. 다만 최종 빌드 후보에 포함된 아이템의 3티어 신발 정규화 자체는 포지션과 관계없이 적용한다.

## 5. 구현 경계

정규화 책임은 외부 DTO나 Raw 데이터 저장 단계가 아니라 `MatchNormalizer`에 둔다.

```text
Raw Match 저장                        변경 없음
Raw Timeline 저장                     변경 없음
MatchParticipant DTO 파싱              roleBoundItem 포함
MatchNormalizer 최종 아이템 추출       역할별 보정 적용
CoreItemPurchaseOrderCalculator        정규화된 2티어 ID로 비교
ChampionBuildStats                     2티어 신발 기준 집계
```

DTO는 Riot 응답을 손실 없이 표현해야 하므로 `roleBoundItem`과 실제 3티어 ID를 그대로 파싱한다. 외부 API의 사실을 서비스의 통계 기준으로 변환하는 작업만 애플리케이션 정규화 단계에서 수행한다.

아이템 처리 순서는 다음과 같다.

```text
item0 ~ item5 추출
        ↓
null과 0 제거
        ↓
3티어 신발을 구매한 신발 ID로 치환
        ↓
코어 아이템 ID만 유지
        ↓
중복 제거
        ↓
Timeline 구매 순서 계산
```

신발 정규화는 코어 아이템 필터링과 중복 제거보다 먼저 수행한다. 그래야 비교와 통계에 실제 구매 기준인 신발 ID가 일관되게 남는다. 정규화에 포지션이나 퀘스트 완료 정보가 필요하지 않으므로 `ITEM_DESTROYED 1201` 이벤트를 별도로 확인할 필요도 없다.

## 6. 검증 항목

- Match 최종 아이템이 `3175`이고 Timeline에 `3020` 구매만 있어도 구매 순서가 완전한 것으로 계산된다.
- 구매 순서와 `buildKey`에는 `3175`가 아닌 `3020`이 들어간다.
- 모든 지원 3티어 신발이 대응하는 실제 구매 신발 ID로 정규화된다.
- 참가자의 `teamPosition`과 관계없이 같은 정규화 결과가 나온다.
- `3176`은 자동 변환 중간 상태인 `3013`이 아니라 실제 구매 아이템 `3010`으로 정규화된다.
- 최종 Match에 구매 신발 ID가 그대로 남은 게임은 기존과 동일하게 처리된다.
- BOTTOM의 `roleBoundItem` 신발이 `item0~item5`에 없어도 최종 빌드와 구매 순서에 포함된다.
- BOTTOM 퀘스트 완료 시 신발의 `ITEM_DESTROYED` 이벤트가 있어도 기존 구매 기록은 제거되지 않는다.
- TOP, JUNGLE, SUPPORT의 `roleBoundItem`은 현재 최종 빌드에 추가되지 않는다.
- 동일 신발이 일반 슬롯과 `roleBoundItem`에 동시에 나타나도 중복 저장되지 않는다.
- Raw Match와 Raw Timeline JSON은 정규화 전후에 변경되지 않는다.

## 7. 재검토 조건

다음 요구사항이 생기면 가상 이벤트 방식 또는 별도의 업그레이드 이력 모델을 다시 검토한다.

- 3티어 신발의 정확한 획득 시점이 필요하다.
- 퀘스트 완료 전후 성능을 시간대별로 분석한다.
- Riot Timeline이 3티어 자동 업그레이드에 대한 명시적 이벤트를 제공하기 시작한다.
- 실제 최종 인벤토리만으로 통계를 조회해야 한다.
- 아이템 메타데이터에서 신발 업그레이드 관계를 안정적으로 제공하지 않게 된다.
